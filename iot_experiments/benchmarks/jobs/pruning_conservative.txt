# Conservative-pruning batch — GPU-only (hello/torch scan + cupdlpx master). QUEUE THIS ON THE A100.
#
# WHY: on the target first-order master (cupdlpx), the planted Monge instances CYCLE under the default
#   pruning (tolerance and hysteresis both 0/7 locally), and only prune=none converges (7/7) -- but
#   prune=none lets |F| grow unboundedly, which we cannot afford at scale. tie_break="regularized"
#   (single-solve eps*<r,(theta,f,g)> perturbation) does NOT fix the cycle (0/12 locally, eps in
#   {1e-6,1e-4,1e-2}). Three hypotheses remain, all about making pruning MORE CONSERVATIVE:
#     (H1) a LARGER tau_prune (prune only when the slack is comfortably positive, not ~0);
#     (H2) hysteresis at a larger tau_prune (two consecutive large-slack iterations);
#     (H3) tie_break="regularized" COMBINED with hysteresis + larger tau (maybe together they help).
#
# EVERY job runs the SAME instances three/four ways (the driver records a "prune_false" column =
#   prune=none, and a "default" column = the requested strategy), so each line is self-comparing.
#
# Read the output at: iot_experiments/core/out/planting/<tag>/planting_sweep.json
#   key fields: records[].prune_false.converged, records[].default.converged,
#               records[].default.max_support_over_m_plus_n (edge-set growth), records[].default.iterations
#
# Interpretation guide:
#   - default.converged AND max_support_over_m_plus_n < prune_false's  ->  a WIN: safe pruning that works.
#   - default never converges, prune_false does                        ->  that strategy is unusable here.
#   - both converge but max_support is similar                          ->  pruning buys nothing here.

# ===========================================================================
# (H1) tau_prune sweep, tolerance pruning, cpu-cheap sizes first (do these first, they are fast)
# ===========================================================================
