# gpu_bench batches

**Goal (shifted, from now on).** The target is a **GPU-scalable inverse-OT solver**:
`scan_backend="hello"` (GPU separation) **+ a GPU master (`cupdlpx`)** — i.e. **no NumPy oracle
and no CPU HiGHS** in the target path. HiGHS and `numpy` are kept only as *references* to check
correctness; they are not the scaling story. We accept that this is a different objective than
"beat HiGHS at small size": HiGHS already fails on these LPs on CPU, and a bigger GPU will not
help it.

Two constraints to keep in view:
- the HELLO GPU scan currently supports **`DiagonalWeightFeatures` only**, so GPU-scalable runs
  are `--family diagonal` until we add GPU feature maps for `lowrank`/`quadratic`;
- CuPDLPx returns **~1e-4 duals**, so the loop runs `prune=False` (hysteresis needs accurate
  slacks) and the `1e-9` certificate is unreachable — convergence is read from `is_optimal` /
  `max_violation`, never the solver status.

**Everything on the GPU path is linear memory.** The ground-truth plan `π̂` is generated by
**HELLO** (`plan_backend="hello"`, the default when `--scans hello`), not POT: `O(m+n)` sparse
plan, no `m×n` cost. Certification is a **blockwise** dual check from HELLO's duals
(`core.costs.dual_feasibility`), also `O(m+n)` memory. `plan_backend="pot"` (dense, capped at
`m·n ≤ 2e8`) is a small-`n` *reference* only.

**HiGHS is validation-only and is NOT allowed in the production design.** It cannot run at the
scale the GPU path targets (`n^2.1` LP cost) and it is excluded from the product on purpose. The
production certificate is **HiGHS-free**: one tight FP64 CuPDLPx solve on the final `F`, then an
FP64 `ε`-bound over the whole grid — `v_max + r_support ≤ ε` (weak duality, total mass 1; this is
the shifted-δ repair read as a bound). *The driver for this (`certify.py`) is retired to
`../legacy/gpu_bench_cpu/` because it ran its certificate on the CPU scan; a GPU-scan version is
planned — see the A100 plan.*

Run everything from the repo root. Use `--gpu auto` (first idle), `--gpu <id>`, or
`export CUDA_VISIBLE_DEVICES=<id>` (now respected) to pin one card. An explicit `--gpu <id>`
**refuses a busy card** now (override with `FASTIOT_ALLOW_BUSY_GPU=1`). **Always cap the solvers**
(`--cupdlpx-time-limit`, `--highs-time-limit`).

## Batch 0 — `env` (seconds, run first)

```bash
python -m iot_experiments.gpu_bench.run_batch --batch env --gpu auto
```

Checks GPU/VRAM, torch+CUDA, POT, `pycupdlpx`, HELLO GPU scan, one tiny `is_optimal` run.

## Batch 1 — GPU-only end-to-end loop (the real target)

Runs the **actual algorithm**: `solve_inverse_ot` with the GPU scan and the GPU master, at sizes
where the CPU path gives up. Each record carries a per-iteration **trajectory** (support size,
violation, master/oracle timing), so we can see *what the scaled version succeeds/fails at*.

```bash
python -m iot_experiments.gpu_bench.run_batch --batch e2e --gpu auto \
  --family diagonal --marginal gmm --sizes 3200 6400 12800 \
  --scans hello --masters cupdlpx \
  --plan-backend hello --cupdlpx-time-limit 10 --cupdlpx-warm-start --max-iterations 20 \
  --out iot_experiments/gpu_bench/out/e2e_gpu
```
`--plan-backend hello` is the default here (HELLO π̂, linear memory). `--cupdlpx-warm-start`
reuses CuPDLPx state across iterations (recommended once the loop is master-bound).

Read it as:
- **converged / is_optimal?** — does the GPU loop reach the admissible set at all?
- **master vs oracle per iteration** — which term dominates as `n` grows (expected: oracle
  `O(n²d)` at large `n`, master `O(|F|·K)`);
- **`|F|` growth** (`support_size` in the trajectory) — does `prune=False` let it blow up?
- **iterations** — does it converge or hit `max_iterations`?

## Retired batches (moved to `../legacy/gpu_bench_cpu/`)

The former **Master component ladder** (`--batch gpu_master_k`, was `master_microbench.py`) and
the **build-only probe** (`lp_build_probe.py`) are retired — they are HiGHS-vs-CuPDLPx reference
arms, CPU-bound, and their conclusions are settled (crossover at `|F|≈2–3.5k`; build is cheap).
See `../legacy/gpu_bench_cpu/README.md`. Do not re-run them as target-path measurements.
